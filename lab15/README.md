# ЛР15 — Supabase Authentication і CRUD

Продовження ЛР12: той самий проєкт Supabase і таблиця `public.phones`. Файли ЛР12 збережено без змін. Публічні параметри підключення вже перенесено в `config.js`.

## Налаштування Supabase

1. У SQL Editor проєкту виконайте весь файл `schema_lr15.sql`. Таблиця `phones` має вже існувати після ЛР12. Скрипт не видаляє телефони; створює `user_roles`, функції `private.is_admin()` і `public.check_admin()`, замінює політики таблиці та встановлює привілеї.
2. У Authentication → Sign In / Providers перевірте Email і дозвіл реєстрації. Якщо Confirm Email увімкнено, після реєстрації підтвердьте адресу з листа. У URL Configuration вкажіть фактичну адресу сторінки ЛР15 як Site URL і дозволений Redirect URL, наприклад `https://ВАШ_ЛОГІН.github.io/ВАШ_РЕПОЗИТОРІЙ/lab15/`. Для локальної перевірки додайте адресу Live Server.
3. Створіть два різні облікові записи. Можна зареєструвати їх формою сайту або через Authentication → Users → Add user → Create new user. Для навчальних записів, створених у Dashboard, доступний Auto Confirm User. Паролі обирайте самостійно; у код, GitHub або звіт їх додавати не потрібно.
4. Відкрийте `assign_roles.sql`. Замініть `CHANGE_ADMIN_EMAIL` на адресу адміністратора, `CHANGE_USER_EMAIL` на адресу звичайного користувача. Виконайте цей файл у SQL Editor. Результат покаже адреси й ролі. Збережені паролі для цього не потрібні.
5. Відкрийте сайт через Live Server або GitHub Pages. Увійдіть як адміністратор. Якщо роль змінено під час відкритої сторінки, натисніть «Оновити список»: користувач і роль перевіряться повторно.

Нові реєстрації автоматично не отримують адміністративних прав. Відсутність запису в `user_roles` означає відсутність права запису. Призначення ролей можливе лише довіреним власником через SQL Editor. Не додавайте схему `private` до Exposed schemas. У браузері використовується тільки Publishable key, Secret key і service_role не потрібні.

Після виконання SQL змінюються права спільної таблиці: ЛР12 й надалі читає каталог, але її стара форма анонімного додавання більше не має дозволу запису. Не запускайте повторно `lab12/schema.sql` після налаштування ЛР15: він відновлює стару політику анонімного INSERT. Для повернення правил ЛР15 достатньо повторити `schema_lr15.sql`; уже призначені ролі збережуться.

## Реалізовано

- signUp, signInWithPassword, getUser, signOut, відновлення сеансу та обробка зміни стану автентифікації.
- Гість і user: перегляд, пошук моделі/бренду, фільтр виробника, п’ять способів сортування.
- Admin: додавання, редагування зі скасуванням, видалення з підтвердженням. Перед кожним записом повторно перевіряються користувач і серверна роль.
- Захист на рівні PostgreSQL: SELECT для anon/authenticated; INSERT/UPDATE/DELETE тільки через адміністративні RLS-політики. Браузер не може читати чи змінювати `user_roles`.
- Валідація, повідомлення помилок, порожній каталог і порожній результат пошуку, блокування дій під час запитів, обмеження очікування мережі.

## Перевірка перед здачею

1. Без входу перевірте каталог, пошук, фільтр і сортування; адміністративна форма й кнопки мають бути відсутні.
2. Зареєструйте окремий тестовий обліковий запис. Якщо підтвердження ввімкнено, до підтвердження сеанс не створиться; сайт має показати повідомлення про лист.
3. Увійдіть як user: доступний лише перегляд. Спробуйте неправильний пароль, порожні поля та тимчасову відсутність мережі.
4. Увійдіть як admin: створіть окремий тестовий телефон, відредагуйте, скасуйте інше редагування, видаліть із підтвердженням. Перевірте результат у Table Editor.
5. Для перевірки RLS через DevTools → Console після входу як user виконайте запити нижче. Перший має повернути помилку доступу. Другий і третій можуть повернути порожні масиви без помилки: RLS не відкриває рядки для UPDATE/DELETE. Після цього перевірте, що телефон не змінився. Замініть TEST_PHONE_ID і беріть тільки власний тестовий запис.

```js
await db.from('phones').insert({ model: 'RLS test', brand: 'Test', memory_gb: 128, price: 100 }).select();
await db.from('phones').update({ price: 101 }).eq('id', TEST_PHONE_ID).select();
await db.from('phones').delete().eq('id', TEST_PHONE_ID).select();
await db.from('user_roles').select();
await db.from('user_roles').upsert({ user_id: (await db.auth.getUser()).data.user.id, role: 'admin' });
```

Останні два запити мають бути заборонені. Повторіть спроби запису після виходу: анонімний відвідувач також не повинен змінювати дані. Власник SQL Editor має підвищені права, тому успішний запис у SQL Editor не перевіряє RLS користувача.

## Здавання

Публікуйте всю папку `lab15`, включно з `vendor` і ліцензією бібліотеки. Викладачу потрібні посилання на GitHub Pages і код, SQL-файли та демонстрація двох ролей. Доступ до Supabase Dashboard, пароль бази даних і секретні ключі передавати не потрібно. Якщо потрібен тестовий вхід, узгодьте окремі навчальні облікові записи з викладачем і передайте їх приватно. Автоматична публікація не виконується.
